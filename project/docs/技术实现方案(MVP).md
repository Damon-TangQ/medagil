## 1. 技术架构概览

### 1.1 架构设计理念

与《项目概况(MVP)》一致：**技术方案 = Dify 云服务 + 自研后端 + 微信支付**。平台采用分层架构，具备以下特征：

- **前后端分离**：Web/小程序/管理端为前端，自研后端提供统一 API，Dify 承担 AI 工作流与模型调用。
- **AI 与业务解耦**：智能体能力通过 Dify 编排与调用，业务侧仅负责用户、项目、任务、订阅、积分等。
- **可扩展**：预留扩展能力（如后续自建模型网关、多区域部署），MVP 阶段不引入多余组件。

### 1.2 技术栈选择

以下为 **已确认** 的技术选型，与功能清单及智能体概况一致，不包含未定项。

| 架构层级 | 技术选型 | 说明 |
|----------|----------|------|
| **AI 集成** | **Dify** | 智能体工作流编排、Prompt 管理、多模型调用、流式输出；与《智能体概况(MVP)》中「Dify Workflow 配置」一致。 |
| **向量数据库** | **Zilliz** | 知识库与检索增强的向量存储与相似度检索；与知识库管理、RAG 需求对应。 |
| **Web 前端（用户端 + 管理端）** | Next.js + TypeScript + Radix UI + Tailwind CSS | 用户端与管理端共用同一前端技术栈；支持 SSR/API 路由、组件化与无障碍。 |
| **Web 前端 状态与数据** | Zustand + React Query | 轻量状态管理；服务端状态与缓存。 |
| **小程序端** | Taro + TypeScript + 微信小程序 | 一套代码多端（当前以微信为主）；Mobx 状态管理；UI 可用 Taro UI。 |
| **后端语言与框架** | Go（Gin）+ Python（FastAPI） | Go：用户、项目、订单、支付、积分等业务服务；Python：与 Dify/向量检索/文件解析等 AI 侧对接。 |
| **关系型数据库** | PostgreSQL | 用户、权限、订单、订阅、积分流水等强一致性数据。 |
| **文档/非结构化** | MongoDB | 项目、任务对话、成果库等灵活结构及大文本。 |
| **缓存** | Redis | 会话、热点数据、限流与任务队列。 |
| **API 网关** | APISIX | 路由、鉴权、限流、日志。 |
| **支付** | 微信支付 | 与《项目概况(MVP)》及三端功能清单中的「微信扫码支付」一致。 |

**说明：**

- **不重复、不缺失**：上述列表覆盖《项目概况(MVP)》中的「Dify 云服务 + 自研后端 + 微信支付」，并明确向量库为 Zilliz；前端/后端/数据/网关各一层只列已确定选型。
- **容器与编排**：MVP 阶段可采用 Docker 单机或小型编排；Kubernetes 可作为扩展阶段方案，不在「已确定」技术栈中强制列出。

## 2. 前端技术实现

三端共用同一**业务后端与 Dify**，前端按端拆分实现；各端详细技术方案见下表，文档与对应功能清单一一对应。

| 端 | 技术栈概要 | 详细技术实现方案 |
|----|------------|------------------|
| **Web 用户端** | Next.js 14+、TypeScript、Radix UI、Tailwind CSS、Zustand、React Query | [Web 用户端技术实现方案(MVP)](web/技术实现方案(MVP).md) |
| **管理端** | 与 Web 用户端同一套技术栈；路由与 RBAC 区分 | [管理端技术实现方案(MVP)](admin/技术实现方案(MVP).md) |
| **小程序端** | Taro、TypeScript、Mobx、Taro UI、微信小程序 | [小程序端技术实现方案(MVP)](miniapp/技术实现方案(MVP).md) |

- **Web 用户端**：实现《Web 用户端功能清单(MVP)》中个人中心、搜索、项目管理、成果库、任务对话、导航与组织、会员与订阅；任务对话的流式展示、步骤与思考过程通过对接自研后端与 Dify 实现；文档支持 Word、Excel、PPT、PDF、TXT、Markdown 上传。
- **管理端**：实现《管理端功能清单(MVP)》中 9 大模块（数据看板、用户管理、任务与对话管理、项目与成果、会员与订单、积分、知识库管理、内容与运营、系统设置）；同一前端技术栈，管理端专属路由与 RBAC。
- **小程序端**：实现《小程序端功能清单(MVP)》中与 Web 用户端对齐的 7 大模块；端能力包括微信登录、手机号、分享、微信支付；文档支持以功能清单为准，由后端统一校验与存储。

## 3. 后端技术实现

### 3.1 服务划分与职责

与《管理端功能清单(MVP)》的 9 大模块对应，自研后端负责业务与数据，**不**重复实现 AI 推理（由 Dify 负责）。

| 服务/模块 | 技术栈 | 核心职责 | 对应功能清单 |
|-----------|--------|----------|--------------|
| 用户与认证 | Go + Gin | 微信/手机号登录、用户 CRUD、RBAC 所需用户数据 | 用户管理、系统设置（登录方式、RBAC） |
| 项目与成果 | Go + Gin | 项目 CRUD、多级分类、成果库创建/归档/收藏、列表与搜索 | 项目管理、成果库（用户端）；项目与成果管理（管理端） |
| 任务与对话 | Go + Gin + Python | 任务创建、状态、对话记录存储；调用 Dify 执行任务；步骤与结果落库 | 任务对话（用户端）；任务与对话管理（管理端） |
| 会员与订单 | Go + Gin | 套餐配置、订单流水、支付回调、退款 | 会员与订阅（用户端）；会员与订单管理（管理端） |
| 积分 | Go + Gin | 积分规则、流水、调整、统计 | 积分展示与消耗（用户端）；积分管理（管理端） |
| 知识库服务 | Python + FastAPI | 知识库元数据、分类/标签、版本、权限；调用 Zilliz 做向量写入与检索 | 知识库管理（管理端）；知识库浏览与搜索（用户端） |
| 内容与运营 | Go + Gin | 技能审核、通知与公告、用户反馈处理、模型配置、定时任务管理 | 内容与运营管理（管理端） |
| 系统设置 | Go + Gin | 管理员与角色、操作日志、参数配置、外观与品牌 | 系统设置（管理端） |

**说明**：AI 网关不单独成服务，统一通过 Dify API 调用；流式输出、步骤与思考过程由前端直连 Dify 或经自研后端转发。

### 3.2 数据存储方案

与三端功能及管理端需求一致，不引入未选型存储。

| 存储 | 用途 | 说明 |
|------|------|------|
| **PostgreSQL** | 用户、权限、订单、订阅、积分流水、系统配置 | 强一致性、事务。 |
| **MongoDB** | 项目、任务/对话内容、成果库文档元数据、大文本 | 灵活 Schema、便于扩展。 |
| **Zilliz** | 知识库与 RAG 的向量存储与检索 | 已确定；与 Dify 知识检索可配合（Dify 自带数据集或对接 Zilliz）。 |
| **Redis** | 会话、限流、任务队列、热点缓存 | 会话与性能。 |

**文件存储**：用户上传与生成文件（Word/PDF/图片等）采用对象存储（如 S3 兼容），由自研后端统一管理路径与权限；与「成果库」「知识库管理」中的文件类型一致。

## 4. AI 能力集成（Dify）

### 4.1 Dify 方案定位

与《项目概况(MVP)》一致：**AI 集成采用 Dify**。自研后端不实现模型推理与工作流编排，仅做：

- 业务鉴权与配额（用户/积分/订阅等级）。
- 任务与对话的创建、状态、结果落库。
- 必要时转发请求到 Dify、或由前端在鉴权后直连 Dify。

Dify 侧负责：

- **工作流编排**：与《智能体概况(MVP)》中「Dify Workflow 配置」「结构化 Prompt 设计」「流式输出集成」一致。
- **多模型与调用**：统一模型接入、参数与限流。
- **对话与补全 API**：供前端或自研后端调用，实现任务对话中的「步骤展示」「思考过程」「结果展示」。

### 4.2 与 9 个智能体的对应关系

《智能体概况(MVP)》中的 9 个智能体均在 Dify 上以 Workflow/应用形式实现，技术要点与智能体文档一一对应。

| 智能体 | 技术实现要点（对应智能体概况） | Dify 侧实现方式 |
|--------|--------------------------------|------------------|
| 临床论著助手 | Dify Workflow、结构化 Prompt、文档模板、流式输出 | Workflow：参数提取 → LLM（IMRAD 模板）→ 输出格式化。 |
| 基础论著助手 | 实验类型识别、图表推荐、叙事逻辑模板 | Workflow：方法/结果解析 → 模板与建议生成。 |
| 综述/范围综述助手 | 检索式生成、PRISMA 流程、数据提取表单 | Workflow：检索策略生成 + 文献筛选 + 结构化提取。 |
| 国自然面上基金助手 | 面上项目模板、成果整合、团队画像 | Workflow + 知识库检索（Zilliz/或 Dify 数据集）。 |
| 国自然重点/专项基金助手 | 重点项目模板、多团队协作框架 | Workflow：策略与结构生成。 |
| 博士基础研究课题助手 | 前沿文献追踪、开题报告模板、创新点提炼 | Workflow + 检索。 |
| 博士临床研究课题助手 | 临床研究类型识别、研究设计模板、伦理考量 | Workflow：课题设计与方案生成。 |
| 文献分析助手 | PDF 解析、摘要生成、对比矩阵 | Workflow：文档解析节点 + LLM 总结/对比；PDF 解析可在自研服务或 Dify 插件。 |
| 智能选刊助手 | 期刊数据库、相似度算法、投稿指南 | Workflow：期刊数据检索 + 匹配与推荐。 |

**统一约定**：所有智能体的「核心功能点」与「验收标准」以《智能体概况(MVP)》为准；技术实现不超出该文档与上述对应关系，避免范围蔓延。

## 5. 知识库与向量检索（Zilliz）

### 5.1 知识库与管理端功能对应

与《管理端功能清单(MVP)》中「知识库管理」一致：

- **知识源管理**：PDF、Word、TXT、Markdown 等上传与解析（由自研或 Dify 解析，向量写入 Zilliz）。
- **分类与标签**：多级分类与标签在自研后端维护，与知识库元数据关联。
- **版本控制**：知识库文章修改历史与版本回溯在业务库（PostgreSQL/MongoDB）实现。
- **访问权限**：与用户/订阅等级挂钩，在自研后端做权限校验。
- **使用情况分析**：浏览量、搜索关键词、反馈等由自研后端埋点与统计。

### 5.2 向量存储与检索

**向量数据库已确定采用 Zilliz**。

- **写入**：知识库文档经解析与分段后，由嵌入模型生成向量并写入 Zilliz；嵌入模型可选 Dify 内置或自建，与 Dify 使用方式统一即可。
- **检索**：RAG 检索、知识库搜索、智能体「知识检索」节点，均通过 Zilliz 做向量相似度检索；可结合关键词（混合检索）与重排，由自研知识库服务或 Dify 侧调用 Zilliz API 完成。
- **与 Dify 的关系**：Dify 可使用自身数据集做检索，也可通过 API 使用自研知识库服务（背后为 Zilliz）；MVP 阶段二选一或组合使用，以「知识库管理功能在管理端、检索能力支撑智能体」为目标即可。

## 6. 基础设施与运维

- **部署**：MVP 阶段可采用 Docker Compose 或单机多容器；生产可逐步迁移至 Kubernetes。
- **网关**：APISIX 统一入口、鉴权、限流与日志。
- **监控与告警**：核心服务与 Dify 的可用性、API 耗时、错误率监控；与管理端「数据看板」「系统状态监控」一致，可基于 Prometheus + Grafana 或云厂商监控。
- **日志与审计**：与「系统设置」中的操作日志、安全追溯一致，由自研后端落库与查询。
